# テスト方針

## 採用するフレームワーク

ホストアプリケーションでは、Rails標準のMinitestを使用します。

Solidus本体や一部の周辺ライブラリがRSpecでテストされていても、ホストアプリケーションがRSpecを採用する必要はありません。Solidus本体の内部テストは、アプリケーションのテストスイートには含めず、アプリケーションが追加・変更した振る舞いを検証します。

## テストの配置

```text
test/
  models/       モデルとドメインロジック
  controllers/  コントローラー
  integration/  複数の境界をまたぐ処理
  system/       ブラウザを使った主要ユーザーシナリオ
  helpers/      ヘルパー
  mailers/      メール
```

既存のRailsテスト構成に合わない種類のテストを追加する場合は、配置理由をテストコードまたはこの文書に残します。

## 何をテストするか

### 優先してテストするもの

- アプリケーション固有の業務ルール
- Solidusを拡張した処理
- 自社コードとSolidusの接続部分
- 注文、決済、在庫、会員機能などの重要な利用シナリオ
- Hotwireを含む、ユーザー操作から結果表示までの主要フロー

### 原則として再テストしないもの

Solidusが標準で提供している内部ロジックそのものは、アプリケーション側で同じ内容を重複してテストしません。ただし、設定変更や拡張によって標準動作に影響を与える場合は、アプリケーション側の期待する結果をテストします。

## テストの粒度

テストを固定比率で配分することはしません。高速なモデル・ドメインテストを基礎にし、複数の境界をまたぐ処理は統合テスト、利用者にとって重要な導線はSystem Testで検証します。

System Testだけに依存すると、実行時間と不安定さが増え、失敗原因も追いにくくなります。各テストは、対象の不具合を最小の粒度で再現できる場所に置きます。

## 実行コマンド

```bash
# 通常のテスト
bin/rails test

# ブラウザを使うSystem Test
bin/rails test:system

# 特定のファイル
bin/rails test test/models/example_test.rb
```

## テストデータと外部サービス

外部サービスへ接続するテストは、原則としてテスト環境用のスタブまたはフェイクを使用します。外部サービスとの実際の疎通確認が必要なテストは、通常のテストスイートから分離します。

## CI

CIでは、通常のテストとSystem Testを実行します。テストが失敗した場合は、テストを弱めるのではなく、原因を修正するか、仕様変更に合わせてテストの期待値を更新します。
